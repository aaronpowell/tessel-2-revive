# Tessel 2 Production Image & Release Runbook

This is the capstone document for the OpenWrt uplift: how the **production
firmware image** is built, what is in it, how to flash and validate it on real
hardware, and how to cut a versioned GitHub release. It is the practical
counterpart to [`openwrt-incremental-upgrade.md`](openwrt-incremental-upgrade.md)
(the per-hop 15.05 → 25.12 root-cause roadmap) and
[`openwrt-upgrade-progress.md`](openwrt-upgrade-progress.md) (the narrative
journey).

- **Target OS:** OpenWrt **25.12.5** (r33051), kernel **6.12.94**
- **Device:** Tessel 2 — MediaTek **MT7620N**, `ramips`, MIPS **24KEc** core
  (**no hardware FPU**, soft-float musl userspace)
- **On-device runtime:** **Node.js 8.11.3** (soft-float) + the Tessel JS runtime
  (`t2-firmware @ a22ba2d2`)
- **Status:** fully hardware-validated end to end — boots, `node` runs,
  `t2 run`/`t2 push` deploy and execute JS, and blinky drives LED0/LED1.

The build system lives at [`build/openwrt-incremental/`](../build/openwrt-incremental/).

---

## 1. What the production image contains

A stock upstream OpenWrt 25.12.5 `ramips/mt7620` build, plus a **thin Tessel
overlay** (board DTS + `tessel-tools` package + a handful of kernel patches and
config injections), plus a **baked userspace Node runtime**.

| Layer | What / where |
|-------|--------------|
| OS | OpenWrt 25.12.5, kernel 6.12.94, squashfs + jffs2 overlay |
| Board bring-up | `tessel-tools` (spid = SPI↔coprocessor bridge, usbexecd = USB remote-exec), enabled on boot |
| Node runtime | `/opt/tessel/bin/node` = soft-float Node 8.11.3 + an 8-lib closure under `/opt/tessel/lib`; `/usr/bin/node` = wrapper |
| Tessel JS | `/usr/lib/node/{tessel,tessel-export}.js` (also dup'd under `/opt/tessel/lib/node/`) |
| Release marker | `/etc/tessel-release` (build metadata — see §5) |
| Default hostname | `/etc/uci-defaults/99-tessel-hostname` sets `tessel-<release>-<mac4>` on first boot (see §5) |

### Why Node is lifted, not built in-tree

The factory node is **v4.2.1, uClibc, hard-float** — it cannot run on the modern
musl rootfs and, being hard-float on an FPU-less core, would `SIGILL` anyway.
Building Node 8.11.3 from source directly on 25.12 is a non-starter (gcc-14 vs
the bundled V8 6.2). The working path:

1. Build **soft-float Node 8.11.3** in the in-ladder **OpenWrt 19.07** tree
   (gcc-7.5.0 / musl / python2 — the V8-6.2 era). Its loader soname
   `ld-musl-mipsel-sf.so.1` is **byte-identical** to 25.12's system loader.
2. **Lift** the binary + its 8-lib dependency closure onto 25.12 under
   `/opt/tessel`, isolated via `LD_LIBRARY_PATH` (so its openssl 1.1 never
   clashes with 25.12's openssl 3). No private loader is shipped — musl is
   forward-ABI-compatible and the system loader satisfies `libc.so`.

The payload is regenerated by
[`scripts/extract-node8-payload.sh`](../build/openwrt-incremental/scripts/extract-node8-payload.sh)
and the node-8 JS is tracked in-repo at
[`scripts/tessel-node8-js/`](../build/openwrt-incremental/scripts/tessel-node8-js/).

## 2. The hardware fixes baked in (summary)

Each was root-caused on real hardware over the incremental ladder; full detail is
in [`openwrt-incremental-upgrade.md`](openwrt-incremental-upgrade.md).

| # | Fix | Why |
|---|-----|-----|
| 822 | Shared-SPI-**reset-once** guard (`patches-6.6`, `patches-6.12`) | Flash + coprocessor SPI controllers share `rstctrl` bit 18; the OpenWrt devm refactor dropped the atomic guard → double `device_reset()` → flash reads all-`0xFF` → non-boot. Re-adds the `hw_reset_count` guard. |
| 999 | **CS1 pinmux** (`spi_cs1` = pin 37 only) | Coprocessor moved to `spi@b40`/CS1 → `/dev/spidev1.0`; frees pins 38/39 (fixes the `leds-gpio` probe / POWER LED). |
| spid-start | Runtime **gpiochip-base resolver** | At k6.6+ `gpio-ralink` uses `bgpio_init()` so the SoC gpiochip base moves off 0 (e.g. 512); resolve bank-0 base at runtime instead of hardcoding global GPIO 2/1. |
| spidev | Whitelist compatible **`rohm,dh2228fv`** (k5.15+) | At k5.15 `spidev_of_check()` hard-fails a bare `compatible = "spidev"`; version-gated swap keeps the `/dev` node name unchanged. |
| MTD_SPLIT_FIRMWARE | `=y` injected into the mt7620 kernel fragment | Name-based split of the bare `firmware` partition into kernel + rootfs (19.07 dropped the default) — without it: `unable to mount root fs` panic. |
| **MIPS_FP_SUPPORT** | `=y` injected into the mt7620 kernel fragment | OpenWrt strips the kernel FP emulator; V8's JIT emits `cop1` at **runtime** for JS doubles regardless of the compile-time float ABI, so on the FPU-less 24KEc every `cop1` traps → `SIGILL`. This builds the in-kernel emulator so node runs. |
| dual-binding pinmux | `state_default` carries both `ralink,*` **and** `groups`/`function` | k5.4 pinctrl migrated to the generic DT binding; dual-spelling is all-hop safe. |
| INITRAMFS off | force `# CONFIG_TARGET_ROOTFS_INITRAMFS is not set` | `make defconfig` defaults it **on** for this target → a RAM-root image; must be forced off for a flashable squashfs. |
| LED path | `tessel-export.js` prefix `/sys/class/leds/tessel:` | The old `/sys/devices/leds/leds/tessel:` doesn't exist at k6.12 (gpio-leds device renamed); LED writes silently no-op'd. The canonical `/sys/class/leds/` symlink farm is stable across all kernels. |

Host-side (`t2-cli`, this repo's submodule): `T2_FORCE_FLASH` forced sysupgrade,
version-aware `fixOldUpdateScripts` (`do_upgrade_stage2`), repackaged-restore
flash path, `[sysupgrade]` verbose logging, the `usb-console-*.js` tools, and
`SUPPORTED_DEVICES := tessel,tessel2 tessel tessel2`.

> **Note:** `libgpiod` was **never** needed anywhere on the 15.05 → 25.12 ladder —
> `CONFIG_GPIO_SYSFS=y` survives through k6.12.

## 3. Building the production image

Prerequisites: Docker (the build runs in an Ubuntu 18.04 container) and a
prebuilt node-8 payload (`output/tessel-node8-payload.tar.gz`), regenerated by
`scripts/extract-node8-payload.sh` from a built 19.07 node + the tracked node-8
JS.

```bash
cd build/openwrt-incremental

# Build the golden 25.12 production image.
OPENWRT_TAG=v25.12.5 \
TESSEL_PROD=1 \
TESSEL_NODE_PAYLOAD=/artifacts/tessel-node8-payload.tar.gz \
TESSEL_RELEASE=v25.12.5-node8-r1 \
docker compose run --rm build
```

Key `build.sh` environment flags:

| Flag | Meaning |
|------|---------|
| `OPENWRT_TAG` | Upstream OpenWrt release tag (e.g. `v25.12.5`) — also selects the kernel patch dir and feed branch |
| `TESSEL_PROD=1` | Bake the Node 8.11.3 runtime + `/etc/tessel-release` (the production image) |
| `TESSEL_RELEASE` | Release string written into `/etc/tessel-release` (bump `-r2`, `-r3`, … for future rebuilds on the same OpenWrt base) |
| `TESSEL_NODE_PAYLOAD` | Path to the prebuilt node-8 payload tarball |
| `TESSEL_DIAG=1` | (Non-prod) bake the Wi-Fi-AP diagnostic overlay |
| `TESSEL_INITRAMFS=1` | (Non-prod) also emit a RAM-root initramfs kernel for boot diagnostics |

Output: `build/openwrt-incremental/output/tessel-25.12-PROD-node8-r1.bin`
(a real flashable squashfs sysupgrade image — uImage magic `27 05 19 56` at
offset 0, INITRAMFS off).

## 4. Flashing & validating on hardware

The MT7620 flash path goes over the SAMD21 coprocessor (independent of the
on-device bridge), so a half-written flash is always recoverable by re-running
`restore`. See also
[`build/openwrt-incremental/FLASH-AND-VALIDATE.md`](../build/openwrt-incremental/FLASH-AND-VALIDATE.md).

1. **Repackage** the image into a restore tarball (u-boot member + the
   sysupgrade member): `new_build_2512-prod-node8-r1.tar.gz`.
2. **Serve** it over local HTTP (e.g. `:8765`).
3. **Flash** from `repos/t2-cli`:
   ```powershell
   $env:T2_FORCE_FLASH='1'
   $env:T2_RESTORE_URL='http://127.0.0.1:8765/new_build_2512-prod-node8-r1.tar.gz'
   node .\bin\tessel-2.js restore --usb
   ```
4. **Power-cycle** — `t2 restore` does **not** reboot the MT7620; a physical
   unplug/replug (~10 s) is required. The first boot after a fresh flash is slow
   (~3 min: jffs2 format + entropy).

### Validation gate

- **OS:** `dd if=/dev/mtd5 bs=64k count=1 | md5sum` ≠ all-`0xFF`; mtd5 starts with
  `hsqs`; `VFS: Mounted root (squashfs filesystem) readonly` (no panic);
  `/dev/spidev1.0` present; `spid` + `usbexecd` steady at boot with no
  `invalid GPIO` errors; host `t2 list --usb` → the device now reports its
  `tessel-<release>-<mac4>` name (no longer the stock `OpenWrt`).
- **Runtime:** `node -e "console.log(process.version)"` → **v8.11.3** (no
  `SIGILL`); `require('tessel')` resolves; `cat /etc/tessel-release` shows the
  metadata; `t2 run` blinky flashes **LED0 (green)** and **LED1 (blue)**.

## 5. Release marker: `/etc/tessel-release`

Baked into the rootfs at build time so multiple releases on the same OpenWrt base
are distinguishable on-device:

```sh
RELEASE="v25.12.5-node8-r1"
BUILD_DATE="2026-07-18T00:00:00Z"
GIT_COMMIT="<short sha>"
OPENWRT_VERSION="25.12.5"
KERNEL_VERSION="6.12.94"
NODE_VERSION="8.11.3"
TESSEL_RUNTIME="t2-firmware@a22ba2d2"
```

It is shell-sourceable (`. /etc/tessel-release`). `RELEASE` comes from the
`TESSEL_RELEASE` build flag; `BUILD_DATE` and `GIT_COMMIT` are computed at build
time.

### Default hostname

The production image ships a first-boot `uci-defaults` script
(`/etc/uci-defaults/99-tessel-hostname`) that sets the device hostname to
**`tessel-<release>-<mac4>`** — the sanitized `RELEASE` (from `/etc/tessel-release`)
plus the last 4 hex of the board's **factory WiFi MAC** (read from the
`factory` MTD partition, the same source the original `Tessel-<MAC>` naming used).
For example `tessel-v25-12-5-node8-r2-fc2c`.
This replaces the stock OpenWrt default (`OpenWrt`) that otherwise shows up in
`t2 list`.

The name is derived **on-device** at first boot (the MAC isn't known at build time)
and includes the MAC tail so two boards flashed with the same release don't collide
on the `<name>.local` mDNS name. The suffix comes from the factory partition rather
than `eth0`'s address because on this board `eth0` is assigned a **random,
locally-administered MAC each boot**, which would make the suffix meaningless (it can
even latch onto a transient USB-gadget interface). The factory MAC lives in flash, so
it is stable across reboots and power-cycles. If the factory partition can't be read
the script falls back to the first real netdev MAC.

> **Note — the factory MAC is not permanent across a `t2 restore`.** It isn't a
> vendor-burned address: `t2 restore` bulk-erases the flash and writes a *freshly
> randomised* factory partition (`02:a3:<4 random bytes>`, see
> `t2-cli/lib/tessel/restore.js`). So a destructive restore gives the board a new MAC
> and therefore a new `-<mac4>` suffix. Within the life of one install the name is
> stable; don't treat the suffix as a permanent serial number.

`uci-defaults` scripts run once and are then whited
out of the read-only squashfs, so this **never** clobbers a later rename — change the
name anytime with:

```bash
t2 rename <name>          # persists to the jffs2 overlay
# or on-device:
uci set system.@system[0].hostname='<name>'; uci commit system
```

## 6. Cutting a new release

1. Make the change (or rebuild on a new OpenWrt base).
2. Build with a bumped `TESSEL_RELEASE` (e.g. `v25.12.5-node8-r2`).
3. Flash + run the full validation gate above on hardware.
4. Commit the build changes, tag `main`:
   ```bash
   git tag -a v25.12.5-node8-r2 -m "Tessel 2 production image r2"
   git push origin v25.12.5-node8-r2
   ```
5. Create a GitHub release for the tag and attach the flashable image
   (`tessel-25.12-PROD-node8-r2.bin`) — the image is **not** committed to git, so
   the release asset is its canonical home.

### Naming

`v<openwrt>-node<major>-r<n>` — the OpenWrt base plus a release counter, so
rebuilds on the same base (`-r2`, `-r3`, …) are cleanly ordered. The matching
`BUILD_DATE` inside `/etc/tessel-release` disambiguates further.
